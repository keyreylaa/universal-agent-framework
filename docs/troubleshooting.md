# Troubleshooting

Every fix below is either exercised by this repository's test suite or read from a named source
file. The **Evidence** column says which; `tests/e2e/omp-discovery.test.mjs` is the only test that
runs a real agent, so anything about Claude Code, Codex CLI, or OpenCode at runtime is
documentation-derived.

## Symptom → cause → fix

| Symptom | Likely cause | Fix | Evidence |
| --- | --- | --- | --- |
| `uaf doctor` prints `No target agent detected`, and `install` fails with `no agents selected. Pass --agents claude,codex,opencode,omp or install a supported agent first.` (exit 2) | Detection needs an agent binary on `PATH` or an existing user config directory (`~/.claude`, `~/.codex`/`$CODEX_HOME`, `~/.config/opencode`, `~/.omp/agent`). A project directory such as `.claude/` only adds a `project:` signal; it does not mark the agent installed. | Pass the agents explicitly: `node core/cli.mjs install --agents claude,codex,opencode,omp --yes`. Detection stays advisory, so an explicit list is always accepted as long as the ids are valid. If you meant the project directory to count, run the agent once so it creates its user config dir. | `core/agents.mjs` (`detectAgents`: `installed = binary or userDir`), `core/cli.mjs` (`cmdDoctor`, `cmdInstall`). The doctor warning path is asserted in `tests/integration/cli.test.mjs`; the detection rule itself is documentation-derived. |
| Skills are installed but the agent does not list them | The agent scans skill directories at session start, so a running session will not see files written underneath it. Secondary causes: the agent reads a different root than the one written (an env override such as `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `OPENCODE_CONFIG_DIR`, or `PI_CODING_AGENT_DIR` points elsewhere), or a skill of the same name exists in a higher-precedence root (`.omp/skills`, `.opencode/skills`) and shadows it. | Restart the agent session — `install` prints this as its closing line. Confirm the roots with `uaf compat`, then check that the expected file exists: `<root>/<skill-name>/SKILL.md`. A skill whose YAML frontmatter is invalid is dropped silently by the agent's loader; see the next row. | Runtime-verified for Oh My Pi only: `tests/e2e/omp-discovery.test.mjs` asserts `omp read skill://code-quality` returns the installed file and that duplicate copies in `.claude/skills` and `.agents/skills` collapse instead of being namespaced. For the other three agents this is derived from `docs/research/*.md` and `docs/compatibility.md`. |
| A skill is silently ignored | Ambiguous YAML frontmatter. The agents parse frontmatter with strict YAML, so an unquoted value containing `": "` becomes a nested mapping, `" #"` is read as a comment, and a tab, a leading YAML indicator character, or unquoted flow brackets in that position are rejected or silently reinterpreted. The framework refuses to install such a skill rather than shipping a file that only fails inside the agent. | Quote the value (`description: "Fix the login: flow"`) and re-run install. Run `uaf skills` from the framework checkout to see per-entry validation errors (it exits 1 when any entry is invalid); `install` also lists `skill <name>: <error>` in its warnings block. | `core/skills.mjs` (`frontmatterIssues`, folded into `loadSkill` errors and into install warnings), `tests/security/adversarial.test.mjs` ("frontmatter cannot smuggle an override line past the strictness check", "a skill is never installed from a source with invalid frontmatter"), `tests/integration/cli.test.mjs` ("skills validates every authored skill and reports the listing budget"), `tests/unit/emit.test.mjs` (command frontmatter must produce no issues). |
| The managed block appears twice in `AGENTS.md` or `CLAUDE.md` | `upsertBlock` replaces the region only when **both** markers are found. If the marker text was reformatted, indented, folded by a Markdown formatter, or one marker was deleted, the block is appended as a second one on the next install. Copy-pasting a block by hand, or merging two branches that each added it, produces the same result. A separate `CLAUDE.md` and `AGENTS.md` each holding one block is normal, not a duplicate. | Delete every stale block except one, restoring the exact marker lines `<!-- uaf:begin v1 -->` and `<!-- uaf:end -->`, then re-run `node core/cli.mjs install --agents <ids> --yes` and check `uaf status` reports no drift. Note that uninstall removes only the first marked region, so a duplicate block survives an uninstall unless you delete it by hand. | `core/manifest.mjs` (`hasBlock`, `upsertBlock`, `removeBlock`). The single-block case is asserted in `tests/integration/install.test.mjs` ("the managed context block is appended, not overwritten, and survives a reinstall"); the duplicate-marker case is documentation-derived. |
| A hand-edited installed file (drift): `uaf status` lists `modified`, and exit code is 1 | The manifest records a content hash per entry. Editing an installed skill, command, runtime file, or the managed block changes that hash, so the artifact is reported as drift instead of being trusted. | Decide deliberately: re-run install to take the framework version (the file is reported as `replaced` and the local edit is lost), or keep the local change and accept that it stays as drift. For a genuinely local skill, author it under a name the framework does not own so it is never part of the managed set. `uaf uninstall` never deletes a drifted file: it reports it as `content changed since install; left in place` and you remove it yourself. Hand edits *inside* the managed block behave differently — uninstall removes the whole marked region, so keep project-specific text outside the markers. | `core/uninstall.mjs` (preserve reasons), `tests/integration/install.test.mjs` ("status reports drift when an installed file is edited by hand", "uninstall removes framework artifacts, preserves user content and hand-edited files"). |
| Install or uninstall is refused without confirmation: `uaf: refusing to proceed without confirmation; re-run with --yes`, exit 2 | Confirmed pipes have no human to read the plan, so both commands require an explicit `--yes` when stdin is not a terminal. Answering `n` at the prompt exits 2 as well. Note that `--json` does not bypass the gate, and that `scripts/uninstall.sh` / `uninstall.ps1` accept a yes flag but do not forward it to the CLI, so a wrapper-driven uninstall always asks its own question. | Add `--yes`: `node core/cli.mjs install --agents <ids> --yes` or `node core/cli.mjs uninstall --yes [--purge]`. For scripts/CI prefer the CLI over the wrappers. To inspect first without any gate, use `--dry-run`. | `core/cli.mjs` (`confirm`), `tests/security/adversarial.test.mjs` (both refusal tests assert exit 2 and that nothing is written or removed). Wrapper argument handling is documentation-derived from `scripts/uninstall.sh` and `scripts/uninstall.ps1`. |
| `uaf search` reports no index: `no index found; run \`uaf index\` first`, exit 1 | `.uaf/index.json` does not exist for the resolved project root. | Build it: `node core/cli.mjs index`. Rebuild with `--force` only when the index is known to be wrong. | `core/cli.mjs` (`cmdSearch`), `tests/integration/cli.test.mjs` ("search without an index fails with an actionable message"). |
| `uaf search` returns nothing for a term that exists | In order of frequency: (1) the index is stale — it was built before the file was added or last changed; (2) the term only appears in the file body — the index stores each file's path, its first meaningful line (skipping blanks and lines starting with `//`, `#`, `*`, `/*`, truncated to 160 chars) and extracted symbol names, so it is not a full-text search; (3) the file was skipped: secret-named, binary, larger than 512 KiB, excluded by `.gitignore`, or inside an excluded directory (`.git`, `node_modules`, `dist`, `build`, `target`, `coverage`, `.venv`, `.uaf`, and others); (4) a single-character term is dropped because terms shorter than two characters are filtered out; (5) a `--kind` or `--language` filter excludes the file. | Re-run `node core/cli.mjs index` and read the `skipped: secret=… binary=… large=…` line it prints. Query a symbol name or a path fragment rather than a phrase from the middle of a file (`uaf search retryWithBackoff`), and drop any `--kind`/`--language` filter. Symbols are only extracted for languages with known patterns, so a name in an unlisted language is matched through the path and headline only. | `core/index.mjs` (`firstMeaningfulLine`, `extractSymbols`, exclusion and skip stats), `core/search.mjs` (`terms` filtered to length > 1; scoring over path, headline, symbols, language), `core/util.mjs` (`DEFAULT_EXCLUDED_DIRS`, `MAX_INDEX_FILE_BYTES`). The working path is asserted in `tests/integration/cli.test.mjs` ("index and search work end to end on a fixture project", including the `no matches` case). |
| A guard blocks a command you intend to run | A `blockedCommands` rule in `.uaf/guard-rules.json` matched. The blocking set is deliberately narrow: `rm-root`, `rm-variable-root`, `mkfs`, `dd-to-device`, `fork-bomb`, `pipe-download-to-shell`, `chmod-world-writable-root`, `force-push-protected-branch`, `gh-repo-delete`, `package-publish`, `global-git-config`, `history-rewrite`, `secret-exfiltration`, `bypass-verify`. Judgement-dependent patterns are `reviewCommands` and only warn. | Edit `.uaf/guard-rules.json`: remove or tighten the offending rule, or move it from `blockedCommands` to `reviewCommands` so it warns instead of blocking. The rules file is data, not code, and `guard-core.mjs` walks up from the hook entrypoint's own directory (or from the session directory for the OpenCode plugin) to find `.uaf/guard-rules.json`; `UAF_GUARD_RULES` can point the guard at a different rules file entirely. Rules are parsed once per process and cached, so restart the agent session for the change to take effect. Never delete the credential-exposure rules to unblock a single command — move that one command out of scope instead. | `hooks/guard-rules.json`, `hooks/guard-core.mjs` (`findRulesFile`, `loadRules`, `evaluateCommand`). `tests/integration/cli.test.mjs` ("the guard blocks a catastrophic command and allows a benign one") exercises the default rules and their exit codes; rule editing itself is documentation-derived. |
| A hook does not fire | Depends on the agent — see the per-agent table below. Common root causes: the entrypoint file was never installed for that agent, the registration file is invalid or was left untouched, or the agent requires an explicit opt-in or trust step. | Check that the entrypoint exists (`.uaf/hooks/claude-guard.mjs`, `.uaf/hooks/codex-guard.mjs`, `.omp/hooks/pre/uaf-guard.ts`, `.opencode/plugin/uaf-guard.ts`) and that the matching registration exists. Install writes those files and reports skipped registrations; see the next table. | `core/emit.mjs` (`planHooksFor`). That the files are written is asserted in `tests/integration/install.test.mjs`; that each agent then executes them is documentation-derived (Oh My Pi hooks are not covered by the e2e test either). |
| `gh preflight` reports `gh-missing` and exits 0 | The GitHub CLI is not on `PATH`, so every remote check (repository metadata, CI status, divergence, outgoing secrets) is skipped. The result is degraded, not failed. | Install `gh` and run `gh auth status`, then re-run `uaf gh`. Until then, treat the local `uaf git --commit` check as the only pre-push guard, and do not publish. | `core/preflight.mjs` (`githubPreflight` sets `degraded: true`, `ok: true`, level `warn`), `tests/unit/preflight.test.mjs` ("degrades gracefully when the GitHub CLI is missing"). |
| A non-git directory | `gitPreflight` reports the error `not-a-repo` (`Not inside a Git work tree.`) and `uaf git` exits 1; `uaf gh` fails earlier at `git remote get-url origin` with `no-remote` and exits 1. `uaf index` roots at the current directory instead of a repository, because the project root is the nearest ancestor containing `.git`. The installed slash commands resolve the vendored CLI with `git rev-parse --show-toplevel`, so in a non-git directory that substitution yields an empty prefix and `node "/.uaf/framework/core/cli.mjs"` fails to load. | `git init` in the project root, or call the CLI by path instead of through an installed command: `node .uaf/framework/core/cli.mjs doctor`. `--cwd <dir>` can point a command at a repository from elsewhere. Nothing is published by a preflight, so a failed preflight in a non-git directory blocks nothing but itself. | `tests/unit/preflight.test.mjs` ("gitPreflight refuses to proceed outside a repository"), `tests/integration/cli.test.mjs` ("gh preflight reports a missing remote instead of claiming success"), `core/util.mjs` (`findProjectRoot`). The slash-command breakage is documentation-derived from `commands/*.md`. |
| `uaf status` says `no install manifest at <root> — nothing is installed here` even though the install succeeded | The command ran under a different scope root: a project-scope install records the manifest in `<project>/.uaf/install.json`, a user-scope install in `~/.uaf/install.json`. The resolved root also changes with the working directory, because the project root is the nearest ancestor containing `.git`. | Re-run from the same directory and scope: `uaf status` for project scope, `uaf status --scope user` for user scope. Use `uaf doctor` to print the resolved `projectRoot` alongside the framework root. | `core/cli.mjs` (`cmdStatus`, `cmdDoctor`), `core/manifest.mjs` (`manifestPath`), `tests/integration/install.test.mjs` (project- and user-scope manifests are asserted separately, including that a user-scope install never touches the project). |
| `uaf status` reports an entry as `missing` | A tracked artifact was deleted or moved after install, so the installed set no longer matches the manifest. | Re-run install to restore it, or `uaf uninstall --yes` and reinstall cleanly if the manifest itself is stale. Both `uaf status` and `uaf doctor` exit/signal the drift, so nothing is silently repaired. | `core/uninstall.mjs` (`describeManifest` classifies `missing` versus `modified`), `tests/integration/install.test.mjs` (drift states and the `entries`/`drift` shape). |
| `install` reports the Claude hook registration as `skipped` with `is not valid JSON; left untouched (Claude Code rejects comments and trailing commas)` | `.claude/settings.json` is not strict JSON, so appending the `hooks.PreToolUse` entry would corrupt a file Claude Code rejects anyway. The installer deliberately leaves it alone. | Fix the JSON (remove comments and trailing commas), then re-run install. Unrelated keys and existing permissions are preserved: the installer only appends one entry, and uninstall removes exactly that entry. | `core/emit.mjs` (`json-array-append` skip path), `tests/integration/install.test.mjs` ("invalid existing Claude settings are left untouched and reported", "existing Claude settings are preserved and only the hook entry is added"). |
| `install` warns `codex: project-scope commands are unsupported by this agent …` | Codex documents only user-scope prompts (`$CODEX_HOME/prompts/*.md`); there is no project-level prompt directory, so the installer refuses to invent one. | Nothing to fix. At project scope the same workflows are available to Codex as skills in `.agents/skills`; use `--scope user` if you want prompt files in `$CODEX_HOME/prompts/`. | `tests/unit/emit.test.mjs` ("planInstall reports Codex project-scope commands as unsupported instead of writing them"), `core/agents.mjs` (`codex.commands.project` is `null`). |
| An agent refuses to run the `curl … | sh` bootstrap | The hook policy blocks piping a download into a shell (`pipe-download-to-shell` in `.uaf/guard-rules.json`), which is the intended behaviour: an agent should not execute unreviewed remote code unattended. | Run the bootstrap yourself in a terminal, or have the agent fetch the script to a file, show it to you, and run it after you approve. To allow it deliberately, remove the rule from `.uaf/guard-rules.json`. | Rule text in `hooks/guard-rules.json`; the guard entrypoints in `tests/integration/cli.test.mjs` assert that a blocked command exits 2. |

## Hook not firing: per-agent causes and fixes

| Agent | Cause | Fix | Evidence |
| --- | --- | --- | --- |
| Claude Code | `.claude/settings.json` must be strict JSON. A comment or trailing comma is a settings error, and the installer skips a file it cannot parse instead of rewriting it. The guard blocks with exit code 2 and feeds stderr back to the model. | Repair the JSON, re-run install, confirm the `PreToolUse` entry exists under `"hooks"` and that `command` points at `node <root>/.uaf/hooks/claude-guard.mjs`. | `core/agents.mjs` (claude notes, citation to `docs/research/claude-code.md` §5), `tests/integration/install.test.mjs` (entry appended; invalid JSON skipped). Runtime firing is documentation-derived. |
| Codex CLI | Hooks require the `features.hooks` setting, and a non-managed hook must be reviewed and trusted per definition hash before Codex will run it. `.codex/hooks.json` is also write-if-absent, so an existing file was left untouched. | Enable `features.hooks` in `$CODEX_HOME/config.toml`, run the one-time `/hooks` trust review, and merge the `PreToolUse` entry into any pre-existing `.codex/hooks.json` by hand (the installer will not overwrite it). Codex hook input/output is only partially documented, so treat the guard as advisory. | `core/emit.mjs` (write-if-absent with the reason string), `tests/integration/install.test.mjs` ("an existing Codex hooks.json is never overwritten"), `docs/compatibility.md` (known gaps). |
| Oh My Pi | Discovery is `<root>/hooks/{pre,post}/*.{ts,js}` only. A file placed directly in `.omp/hooks/` is never loaded. | Keep the entrypoint at `.omp/hooks/pre/uaf-guard.ts` and do not move it up a level. Under the user root the directory is `<agentDir>/hooks/pre/`. A throwing `tool_call` handler fails closed, so an error in the entrypoint blocks tools rather than silently disabling the guard. | `hooks/omp-guard.ts` (installed path comment), `core/agents.mjs` (omp hooks citation to `omp://hooks.md`), `tests/integration/install.test.mjs` (entrypoint written). Discovery itself is documentation-derived. |
| OpenCode | OpenCode has no declarative hook system; interception exists only through plugins, so the entrypoint must live in the plugin directory the loader scans. OpenCode 2 additionally refuses a plugin whose module default export is not `{ id, setup }` (or `{ id, effect }`); a V1 entrypoint that only names an export never loads, and the server log records `Plugin must export a default definition with an id and an effect or setup function`. | Keep the file at `.opencode/plugin/uaf-guard.ts` (the loader also accepts `.opencode/plugins`). The plugin default-exports `{ id: "uaf-guard", setup }`; a block is reported by throwing from the `ctx.tool.hook("execute.before", …)` callback, and a missing rules file warns on `session.created` instead of registering the hook. | `hooks/opencode-guard.ts`, `core/agents.mjs` (opencode hooks citation to `docs/research/opencode.md` §4, §10), `tests/integration/install.test.mjs` (the plugin file is written, its default export is loaded, and the registered hook blocks). Runtime firing against a live server is documentation-derived. |
